# N빵 정산 봇 인터뷰 프로토콜 및 로그

## A. 인터뷰 프로토콜

- **대상(누구를, 왜)**

최근 1개월 이내 2차 이상의 복합 모임에서 직접 총무를 맡아 N빵 정산을 해본 대학생 및 직장인

- **알아내려는 것(가설)**

정산의 피로는 단순 계산이 아니라 **차수별 중도 참석자 조율**과 **지불 지연 시 정산 독촉의 심리적 부담**에 존재한다.

- **질문 5개 - 과거 행동을 묻는 형태로**

과거의 실제 행동과 상황을 확인하는 방식으로 질문한다.
1. 가장 최근에 여러 명이 모인 자리에서 비용을 직접 정산했던 때 얘기를 들려주세요. 모임 시작부터 정산이 끝날 때까지 어떻게 진행됐나요?
2. 그때 각자 내야 할 금액은 실제로 어떻게 계산하셨나요? 계산하면서 자료를 보거나 고친 부분이 있었나요?
3. 그 정산 과정에서 가장 시간이 오래 걸리거나 여러 번 확인해야 했던 부분은 무엇이었나요?
4. 최근에 정산 금액을 알려준 뒤 바로 돈을 보내지 않은 사람이 있었던 적이 있나요? 그때 어떻게 하셨나요?
5. 돈을 다시 요청하셨다면 언제, 어떤 방식으로 하셨나요? 피하고 싶었던 상황이 있었나요?

### 왜 이렇게 썼나

**대상을 "정산에 참여한 사람"이 아닌 "정산을 직접 진행한 총무 역할을 맡은 사람"으로 좁혔다.** 정산을 직접 진행해보지 않은 사람은 정산할 때의 고충을 정확히 알 수 없어 

### 조심할 유도 질문
- 피해야 할 질문: "영수증 찍으면 알아서 계산해 주고 카톡 문구 써주는 앱 나오면 쓰실 건가요?"
- 사실 확인 질문: "지난번 모임 정산 때 늦게 보낸 사람에게 카톡을 보낼 때 구체적으로 뭐라고 적어 보내셨나요?"

**도출된 페인 (누적)**

1. **복합 정산의 계산 부담** [문제] - 개인별 소비 항목이나 금액이 다르고 N분의 1과 차액 정산이 섞이면, 각 참여자의 부담액을 직접 계산하고 반복적으로 확인해야 함. 정산 건수가 늘어날수록 계산과 확인 작업량도 증가함. (로그 2, 5, 6, 7)

`개인별금액상이` > `차액정산` > `수동계산` 패턴 반복

2. **참여 시점 변화에 따른 정산 기준의 모호성** [제약] - 차수별 참여자가 다르거나 중간에 합류·이탈하는 경우, 특정 참여자에게 어느 시점까지 발생한 비용을 부담시켜야 하는지 판단하기 어려워짐. 잘못 포함할 경우 참여자의 이의제기로 이어질 수 있음. (로그 12, 15)

3. **정산 내역의 추적·검증 부담** [문제][우회로] - 정산 담당자는 중복 청구나 누락을 방지하기 위해 영수증을 촬영하고 지출 내용을 별도로 기록하며, 이미 올린 정산 내역을 반복적으로 확인한다. (로그 1, 2, 4)

4. **기존 정산 도구와 실제 정산 상황의 불일치** [제약] [우회로] - 기존 정산 기능으로 처리하기 어려운 상황에서는 개별 정산으로 전환하거나 별도의 설명 메시지를 작성해야 하며, 송금 방식이 다를 경우 입금 확인과 완료 처리를 수동으로 맞춰야 함. (로그 3, 14, 16)

5. **미입금자의 추적 및 재요청 부담** [문제][우회로] - 정산 요청 후 즉시 송금하지 않은 참여자가 있으면 일정 기간 기다렸다가 개인적으로 다시 연락하거나, 상대방이 송금 가능한 시점을 기억했다가 계좌의 금액을 재전달해야 함. (로그 11, 13)

6. **관계·금액·정산 기준에 따른 사회적 부담** [문제][제약] - 정산 요청 여부와 방식은 단순히 미입금 여부만으로 결정되지 않고 상대방과의 관계, 금액 크기, 비욜 발생 당시의 참여 여부 등의 맥락에 영향을 받음. 실제로 소액이라는 이유와 후배라는 관계때문에 요청을 포기하고 본인이 대신 부담하거나, 부담액에 대한 이의를 설명하는 과정에서 심리적 부담이 발생했다. (로그 9, 15)

### 보존해야 할 부정적/경계 증거

1. **단순 N분의 1 정산은 기존 도구로 해결 가능함** - 동일하게 소비한 지출의 경우처럼 참여자별 부담액이 동일한 상황에서는 기존 카카오톡 정산 기능으로 별다른 어려움 없이 처리했다. (로그 8)

2. **극소액의 정확한 분배는 중요도가 낮을 수 있음** - 나누어떨어지지 않는 1원 단위 금액은 정확하게 맞추기보다 의도적으로 제외했다. (로그 10)

### 💬 왜 이렇게 썼나

- **인용문에서 사용자가 실제로 수행한 행동과 그 결과를 중심으로 태그를 추출했다.** 수동계산, 영수증촬영, 개인연락, 수동완료체크처럼 사용자가 실제 과거 정산에서 수행한 행동을 우선적으로 추출했다. “자동 정산이 필요하다”처럼 인터뷰에서 직접 확인되지 않은 솔루션은 태그로 만들지 않았다.

- **하나의 로그에서 여러 개의 태그와 페인이 도출될 수 있도록 했다.** 예를 들어 로그 14는 단순히 “카카오뱅크 사용 불가”의 문제가 아니라 `송금수단상이` → `수동입금확인` → `수동완료체크` → `확인누락`이라는 하나의 실제 작업 흐름을 보여준다. 따라서 개별 문장을 하나의 문제로 단순화하지 않고 행동과 결과를 함께 기록했다.

- **태그는 해결책이 아니라 관찰된 사실의 색인으로 사용했다.** OCR필요, AI정산필요, 자동독촉필요처럼 현재 기획 중인 기능을 태그로 사용하지 않았다. 대신 영수증촬영, 수동계산, 대기후독촉 등 원문으로 다시 추적할 수 있는 표현을 사용했다.

- **비슷해 보이는 계산 문제도 서로 다른 원인으로 구분했다.** 개인별 소비 금액 차이로 발생하는 계산 부담(로그 2, 5, 6, 7)과 참여자의 중도 합류·이탈로 발생하는 정산 기준의 모호성(로그 12, 15)은 필요한 해결 방식이 다를 수 있으므로 하나의 복잡한 정산 범주로 합치지 않았다.

- **정산 완료까지의 전체 Workflow를 분석했다.** 문제를 단순히 개인별 부담액 계산에서 끝내지 않고 지출 기록 → 계산 → 정산 요청 → 입금 확인 → 미입금자 재요청 → 완료 처리까지 추적했다. 그 결과 계산 부담뿐 아니라 중복·누락 확인, 송금 상태 확인, 재요청 등의 추가적인 수작업을 발견할 수 있었다.

- **사용자의 관계와 상황에서 발생하는 사회적 부담을 별도로 구분했다.** 로그 9에서는 후배와 소액이라는 조건 때문에 정산 요청 자체를 포기하고 본인이 비용을 부담했고, 로그 15에서는 참여 시점에 따른 정산 이의를 설명하는 과정에서 부담을 경험했다. 따라서 사회적 부담을 단순한 “독촉 메시지 작성의 어려움”으로 한정하지 않고 정산 요청·조율 과정 전반의 문제로 보았다.

- **기존 도구가 잘 작동한 사례와 중요도가 낮은 문제도 제거하지 않았다.** 로그 8에서는 단순 N분의 1 정산이 기존 카카오톡 기능으로 처리되었으며, 로그 10에서는 1원 단위 차이를 사용자가 문제로 여기지 않았다. 이러한 사례는 모든 정산 상황에 새로운 해결책이 필요한 것은 아니라는 점을 보여주며, 해결해야 할 문제의 범위를 복합 정산 상황으로 좁히는 근거로 사용했다.

- **모든 누적 페인을 원본 로그 번호로 추적할 수 있도록 했다.** 이후 도메인 온톨로지의 개념·관계·속성·규칙을 정의할 때 evidence:에 해당 로그 번호를 연결하여, 각 온톨로지 요소가 실제 인터뷰의 어떤 발화에서 도출되었는지 다시 확인할 수 있도록 한다.

## D. 핵심 Job Story
> 여럿이 모인 복합 술자리 총무를 맡았을 때, 나는 차수별 참석자를 반영해 정확히 계산하고 앙금 없이 빠르게 돈을 받고 싶다. 그래서 민망하게 돈을 재촉하거나 손해보지 않고 정산을 끝낼 수 있도록. (로그 1, 3, 4)
