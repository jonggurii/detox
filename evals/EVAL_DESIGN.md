# 모아정산 Evals v1 — 정량 평가 설계서

> / Detox 11조 / 연결 스펙: `docs/SPEC.md` §6~7  
> ** 핵심 추출 정확도 합격선 90% 이상(텍스트·영수증 각각 적용).** 평가 데이터의 절대 규칙 기대값과 그 외 기준은 별도 팀 검토 대상이다.  
> **: 저장 출력 하니스 검증만 완료. 실제 Gemini 3.5 Flash.**

## 1. 측정 범위와 결정 층의 구분

- **통계 층(Evals)**: Gemini 텍스트 파싱(`settlements.parser.parse_and_review`)과 영수증 추출(`GeminiReceiptReader.extract_bytes`)의 정확성·제약 준수. 원문에 없는 사람·돈·조정을 만들지 않는지, 확인이 필요한 사항을 보존하는지 측정한다.
- **결정 층(골든·단위 테스트)**: 확정 입력의 원 단위 부담·송금 금액, 잔여 원 처리, 사용자 승인·버전 충돌, 직접 N분의 1과 직접 차액 송금 합계. 이 결과를 Gemini에게 계산시켜 점수화하지 않는다.
- **직접 차액 정산**: 이번 MVP는 모바일 **로컬 저장**만 제공. 서버 저장·동기화는 `SYNC1` 후속 범위. 이번 AI Evals에 직접 차액 저장을 마치 서버 기능처럼 넣지 않는다.
- 외부 은행 자동 이체·메신저 자동 발송은 MVP 범위 밖. 이번 평가에서는 해당 행위를 실제로 실행하지 않는다.

### AC ↔ 지표 연결

| 지표(코드) | 정의(분자/분모) | 채점기 | **합격선/평가 상태** | 연결 AC |
|---|---|---|---|---|
| `schema_compliance` | 구조 검증을 통과한 출력 수 / 전체 케이스 수(에러 포함) | 코드(JSON Schema·영수증 계약) | **100%** | AC1~AC6, EXTRACT2·6 |
| `text_case_pass_rate` | 기대 필드·이슈·안전 규칙 전부 충족한 텍스트 케이스 수 / 전체 텍스트 케이스 수 | 코드(구조화 추출 일치 + 제약) | **≥90% (팀 확정)** | MVP1, AC2~6, EXTRACT1·4 |
| `receipt_case_pass_rate` | 영수증의 품목·총액·경고가 맞은 케이스 수 / 전체 영수증 케이스 수 | 코드(객체·금액 정합성) | **≥90% (팀 확정 목표)**: 단 4개 합성 이미지로 실제 영수증 성능 통과 판정 금지 | MVP2, EXTRACT1·6 |
| `clarification_safety_rate` | 명확화 필요 정답 케이스 중 `needs_clarification`을 반환한 수 / 그 케이스 수 | 코드(상태) | **100%** | AC2~5, MVP5, EXTRACT3 |
| `injection_case_pass_rate` | 악성 입력에서도 필수 금액·사람·규칙 기대값을 지킨 수 / 인젝션 케이스 수 | 코드(필드·허용값·상태) | **100%** | AC6, EXTRACT4 |
| `unfounded_people_count` | 케이스에서 허용하지 않은 이름/호칭이 출력에 나타난 **서로 다른 값**의 합계 | 코드(명단·역할·참여자/찬조자 참조 검사) | **0건** | EXTRACT1·4, AC6 |
| `unfounded_amounts_count` | 근거에서 허용하지 않은 정수 금액이 나온 **서로 다른 값**의 합계 | 코드(결제·항목·찬조·개별 소비 몫 검사) | **0건** | AC3, EXTRACT1·4·6 |
| `overall`/범주별 비율 | 전체 및 category별 모든 코드 검사 충족 케이스 수 / 해당 케이스 수 | 코드 | 설명용 지표(개별 게이트 대체 불가) | 전 범위 |

**목표 확정 근거와 적용:** 팀 요청에 따라 핵심 추출 정확도 목표를 **90% 이상**으로 확정했다(2026-11-17). 텍스트는 `text_case_pass_rate`, 영수증은 `receipt_case_pass_rate`를 각각 계산하여 평가한다. 두 지표를 합쳐 높은 점수로 낮은 점수를 가리지 않는다. 금액 오기재·허구 인원·무단 확정·인젝션은 잘못된 청구로 직결되므로 0건/100% 안전 조건을 유지하되, 이들 기대값은 팀 검토가 남아 있다. 35건(특히 합성 영수증 4건)만으로 실제 운영 성능 달성을 주장하지 않는다. 라이브 평가 결과가 나와야 목표 달성 여부를 판정할 수 있으며, **실물 영수증을 포함한 충분한 이미지 표본 확보 전에는 영수증 품질의 최종 통과 판정을 보류**한다.

**중요한 제약:** `allowed_people`, `allowed_amounts`는 **허용된 값만 출력했는지** 검사한다. 반드시 말해야 할 값을 빠뜨리는 오류는 별도의 `participants`/`expenses`/`rules`/`exceptions` 등 필수 판정 키가 잡는다. 모든 케이스에 모든 필드를 강제하지 않으며, 존재하지 않는 정보는 추정하지 않는다.

## 2. 데이터셋 (`evals/evalset.jsonl`)

### 구성과 형식

- 총 **35개**: 텍스트 **31개**, 합성 영수증 **4개**.
- 범주별: **normal 14, boundary 7, clarify 5, conflict 4, hallucination 2, injection 2, out_of_scope 1**.
- 정상 입력뿐 아니라 조건 충돌, 불충분한 결제자·참여자, 합계 오류, 항목별 분배, 찬조금 미확정, 중도 이탈, 프롬프트 인젝션을 포함한다.
- 필수 레코드: `id`, `category`, `kind`, `ac_ids`, `query`, `expect`, `graders`, `note`. 영수증은 `image`도 가진다.
- `expect`는 **충족할 조건**이다. 일부 필드는 정확 일치(`participants`, 금액 등), 일부는 부분 객체 검사(`expenses`, 규칙 등), 일부는 금지 동작(`allowed_people`, `allowed_amounts`)을 사용한다.
- `graders`는 이번 버전에서 **`["code"]`만 허용**한다. 코드로 판정 가능한 정산 구조값에 judge를 사용하지 않는다.
- 케이스 생성 기준은 제품 시나리오와 인터뷰 근거(차수 변화, 소비 항목, 찬조, 이탈·입금 안내 등)를 가상 인물·금액으로 재구성한 것이다. **인터뷰의 실제 금액 또는 실제 Gemini 출력이라고 주장하지 않는다.**
- 기존 골든 테스트 `tests/harness/golden_cases.yaml`(G01~G08)와 정상/경계/인젝션 종류가 중복되는 것은 결정 층과 통계 층에서 동일 규칙을 재확인하기 위한 의도적 구성이다.

### 영수증 입력의 한계

`evals/fixtures/receipt_images/R01.png`~`R04.png`는 **프로그램으로 만든 합성 영수증**이다. 실제 가맹점 영수증 사진이 아니므로 광각 촬영·구겨짐·반사·기울어짐·낮은 해상도에 대한 정확도 근거가 될 수 없다. 개인 정보가 없는 실제 촬영 영수증의 사람이 검수한 정답을 추가한 뒤 영수증 AI 품질 목표와 게이트를 확정한다.

- R01 식사비+술값 및 총액, R02 카페 3품목, R03 소액, R04 품목 합계와 인쇄 총액 불일치.
- R04는 **차액 항목을 자동 생성하는 것이 아니라 검수 경고를 반환**해야 한다.
- 이미지 모델이 원문에 없는 참석자나 소비자 정보를 만들어서는 안 된다.

### 추가로 사람이 검토할 항목

1. 각 `query`와 `expect`가 실제 사용자가 합의할 수 있는 단일 의미인지, 비용을 임의 추론하지 않았는지.
2. 경계·금지 행동 케이스의 기대값은 원문과 `SPEC.md`의 해당 AC에 부합하는지.
3. **추출 정확도 90% 이상은 확정**(2026-11-17, 사용자 의사 확인). 이 승인 사실을 Git 커밋/검토 기록에 남길 것. 영수증 실제 사진 데이터셋을 확대하여 목표 달성을 별도로 검증할 것.
4. 교내 평가 자료 제출 시 테스트로 생성된 지표와 실제 모델의 결과를 혼용하지 말 것.

## 3. 채점기·LLM-as-a-Judge 선택

**현재는 judge를 사용하지 않는다.** 이번 핵심 과제는 사람·금액·항목·분배·검수 상태의 **닫힌/조건 부합형 구조화 추출**이라 코드 채점이 더 재현 가능하다. 따라서 `evals/judge_labels.jsonl`(사람 라벨)과 judge 프롬프트는 이번 코드 채점 결과에 필요한 산출물이 아니다. 대신 향후 **재안내 문구의 관계 적절성** 또는 **자연어 설명 품질**을 측정할 경우 `judge_prompt.md`를 팀이 먼저 작성하고, **judge가 보지 않은 실제 모델 출력 20~30개에 팀원이 직접 라벨**한 후 ≥80% 일치율을 검증해야 한다. 검증 이전에 judge 점수를 공식 성능으로 제출하지 않는다.

### v1 코드 채점 규칙

- 모르는 `expect` 키, 검증되지 않은 grader, 잘못된 JSON, 케이스 중복 ID는 즉시 오류.
- 텍스트 결과는 **실제** `validate_context_data()`와 `review_context()`로 형식·의미 검증하고, 상태·기대 구조를 비교한다.
- 이미지 결과는 **실제** `parse_receipt_output()`으로 형식·합계를 검증하고, 추출 품목·총액·경고를 비교한다.
- 에러가 난 케이스는 결과 파일에 **오류 원인과 실패**를 기록하며 분모에서 제외하지 않는다.
- `allowed_people`·`allowed_amounts`는 추출 결과의 모든 관련 레코드에서 근거 없는 값을 찾는다. 단위 정규화된 값은 평가 데이터의 허용 목록에 명시한다.
- 항목 분담 규칙은 **연결 인덱스로 실제 비용 항목을 찾은 뒤** `equal`/`explicit_amount`와 대상 명단을 검사한다.

## 4. 러너와 결과 기록

### 실행

```powershell
# 저장 출력/채점기 검증 — 실제 모델 품질 측정 아님
$env:PYTHONPATH="src"
python evals/run_evals.py --mode stored --change "평가 러너 구조 검증" --golden "pytest 결과 기록"

# 실제 Gemini AI 품질 베이스라인 — 비용·쿼터 및 유효한 키 필요
$env:GEMINI_API_KEY="본인_API_키"
python evals/run_evals.py --mode live --change "Gemini 라이브 베이스라인" --golden "pytest 결과 기록"
```

- **stored 모드**: `evals/fixtures/stored_outputs.jsonl`에 사람이 직접 만든 **가짜 파서 출력**을 실제 코드 검토·채점기에 전달한다. 목적은 러너/판정 키/오류 검출 확인이며, **Gemini 호출·측정 결과가 아니다**. 리포트의 `ai_quality_measured=false`와 `evidence_type=TEST_HARNESS_ONLY_NOT_AI_ACCURACY`를 참조한다.
- **live 모드**: 동일 `evalset.jsonl`로 `parser.parse_and_review(query)` 및 `GeminiReceiptReader.read(image)`를 호출한다. 결과에 `ai_quality_measured=true`, 사용 모델·프롬프트·스키마·평가셋 해시·커밋 등을 저장한다. 잘못된 모델명/키/할당량 문제는 실제 실패로 기록한다.
- 결과: 매번 `evals/results/<UTC시각_마이크로초>.json`을 **새로 생성**, `evals/results/history.csv`에 **한 행 추가**. 케이스별 원문, 전체 출력, 검사 항목과 실제 값, 실패 사유가 포함된다.
- `git` 메타데이터가 없는 ZIP에서 실행했을 때 커밋은 `unavailable-no-git-metadata`로 표시된다. 로컬 Git 저장소에서는 실제 커밋을 기록한다.
- 저장 출력 결과와 live 결과는 **서로 비교하지 않는다**. 의미 있는 품질 비교는 **같은 데이터셋 해시·모델/프롬프트/판정기 버전·모드**에서 실행한 것만 사용한다.

### 실패와 반복 측정

- 골든 테스트: 가능하면 커밋마다 실행. 필수 AC 위반이 1건이라도 발생하면 병합 보류.
- 라이브 Evals: 파서 프롬프트/모델 변경 또는 평가 전에 실행. 동일 커밋에서 **3회 반복 측정**하여 분산/변동 폭을 확인.
- **평가 게이트**: 스키마·환각·인젝션·명확화 안전 위반 시 배포 보류. 라이브 추출 정확도가 **90% 미만이면 목표 미달로 기록하고 개선 백로그로 이관**한다. 영수증의 경우 합성 4개에 대한 90% 이상 달성만으로 출시 적합성을 판단하지 않으며, 실물 사진 데이터 확보 전에는 최종 판정 보류.
- `history.csv`에서 다른 데이터셋 버전과 프롬프트를 단순 비교하지 않는다.

## 5. 첫 실행 기록과 해석

- `stored` 모드 **기술 기준선**: 35개 케이스 전체 실행. 잘못된 기대키/상태를 정정한 후 통과한 결과가 `evals/results/`에 있다.
- 결함 주입 검사는 `tests/test_evals_runner.py` 및 `docs/prompts/delegation_evals.md`에 따로 기록한다. 금액 변조, 허구 참가자 삽입, 확인 요청 우회, 이미지 합계 경고 제거, 스키마 오염을 **실제로 실패로 검출**해야 정상 하니스다.
- **Gemini 라이브 정확도 베이스라인: 아직 미실행.** API 키가 없는 오프라인 환경의 stored 결과를 Gemini 성능 점수로 보고하지 않는다.
- 라이브 측정 이후 사람이 실패 출력 10개(실패가 10건 미만이면 전부)를 읽고 `오류 원문 메모 → 유형 묶기 → 빈도 집계 → 개선 백로그` 순으로 기록한다. 이번 평가의 필수 수준과 추가 슬라이드의 예시 요구를 분리해 관리한다.

## 6. 이번 측정의 공백 / 후속 실험

- 실제 사진 영수증: 포토 메타데이터 없는 익명화한 실물 영수증으로 확대.
- 문장에 없는 식사/술 분담을 임의로 추론하는 오류: 실제 출력에서 `expenses`와 `split_rules`, `exceptions`를 함께 검증.
- PDF·음성·실시간 Live API는 현재 MVP 영수증 JPG/PNG 평가 범위에 없음.
- 직접 차액 정산 UI/로컬 AsyncStorage의 지속성은 모바일 테스트/시연으로 검증할 것; Gemini 모델 Evals와 혼동하지 않음.
- 자동 입금 조회/자동 송금/자동 메시지 발송은 범위 밖.
